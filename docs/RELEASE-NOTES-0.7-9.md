# OVMX V0.7-9 Release Notes

Generated by `tools/gen_release_notes.py` from the merged history since `V0.7-8` (133 commits). Do not hand-edit this file -- re-run the tool against the cut commit instead.

## Highlights

- **A real VAX running OpenVMS V7.3 now joins an OVMX-founded cluster.** OVMX founds the cluster, and the real VAX joins it as a member. OVMX answers the VAX's boot-time closes it used to withhold (vms-db1), and an OVMX-first boot no longer partitions the cluster (vms-d52c, vms-52d). A lost block-transfer REQUEST DATA is retransmitted instead of stalling (vms-c1d). A founding OVMX member now answers a join another member relays to it, so a node that boots last is admitted through any member (vms-6ec). A refused connection-manager send no longer leaves a gap in the message sequence; that gap could crash a real VAX with CNXMGRERR when OVMX joined late (vms-cd8). When OVMX frees a lock resource it mastered, it now removes the resource's entry at the remote directory node as a real VMS master does, so a stale entry at a real VAX no longer leaves a requester waiting on OVMX (vms-e09).
- **Clusterwide logical names** (vms-94a): `LNM$SYSCLUSTER` and `LNM$CLUSTER_TABLE` are executive state, and `LNM$SYSTEM` searches `LNM$SYSCLUSTER` after `LNM$SYSTEM_TABLE`. When another member creates or deletes a clusterwide logical name or table, OVMX applies the change. A node that joins late pulls the cluster's logical-name database from an existing member.
- **The terminal driver is in the executive** on Linux and NetBSD (vms-f8c). DCL, LOGINOUT and `$QIO` reach it: carriage control, VMS line editing and command recall, timed and end-of-file reads, broadcasts, permanent terminal characteristics, and process-permanent files. These are checked against a byte-exact keystroke oracle of a real VAX V7.3 session (vms-370).
- **EDT** line mode and keypad mode, compared against the same oracle.
- **Native VMS images run unchanged:** `.EXE` files LINKed on real OpenVMS Alpha V8.4 and on real VAX V7.3 run on OVMX. On Alpha they reach the rights database, `$CHKPRO` and RMS. On VAX they get page 0 per process through the executive.
- **Process lifecycle:** the executive creates each process before it runs (`$CREPRC`, DCL image tasks and PIPE segments, DEC C `vfork`/`exec`, the TCP/IP auxiliary server's services, PROVISION at boot), and deletes it when it ends. No process registers itself: only its creator (`$CREPRC`) or the boot task's single `ESTABLISH_SYSTEM` makes a VMS process, and the executive refuses any other task (vms-2a5, vms-a2c).
- **No substrate root:** a root audit runs in the acceptance battery on x86_64, Alpha and VAX. TCP/IP services run under their own accounts with an executive-given substrate identity, never root. The setuid-root mount helper is gone.

## Known open items

- **A VAX admitted by an OVMX founder reaching `Username:`** is still in progress: the startup traffic OVMX used to withhold is now answered, but no capture yet shows that VAX completing startup (vms-d52c).
- **Clusterwide logical names** are not sent from OVMX yet: OVMX applies other members' changes and pulls the database, but it does not broadcast its own changes yet. Until it does, a local change to a clusterwide table is refused with SS$_UNSUPPORTED while other members exist (vms-94a follow-up).
- **Lock-tree remastering** between cluster members is not implemented yet.
- **A third node does not join when an OVMX member holds the highest SCSSYSTEMID** in the cluster (vms-6e3).
- **A former master does not yet answer "not master here"** (the 0xf7 reply) to a lock request for a resource it has freed (vms-657).
- **Executive privilege checks** that still read the substrate's credential (`ESTABLISH_SYSTEM`) are being replaced by checks on the process's VMS privileges, and SETIDENT is being confined to a login (vms-a2c). STARTUP and JOB_CONTROL still run as substrate root after boot (vms-137e).
