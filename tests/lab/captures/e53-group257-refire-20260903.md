# E53 group-fix re-fire capture (2026-09-03)

Companion note for `e53-group257-refire-20260903.pcap` (707112 bytes,
3890 SCA frames, `ether proto 0x6007` on vaxlab-2's `br0`, full-window
capture spanning the entire join attempt below).

## Run

- Pod: `vaxlab-2` (ns `ovmx-lab`, k3s-worker, TCG — no `/dev/kvm` in the pod).
- Image: `distro/Dockerfile.bootable` built at `fc-e53-cluster-group@a3a8d387`
  with `--build-arg CLUSTER_AUTH_GROUP=257`, verified byte-exact
  `/etc/ovmx/cluster_authorize.dat` (group=257) staged in the booted
  initramfs.
- Identity: SCSNODE=OVMXJ1, SCSSYSTEMID=1986 (mk_sysgen --alloc,
  collision-guarded against the pod's reserved 1025/1026/1027).
- CAP_NET_RAW dropped from the whole booted-OVMX QEMU subtree (verified:
  CapEff/CapBnd both clear net_raw) — a join can only be the executive's
  kernel L2 I/O, not the pod's ambient capability.
- VAX1/VAX2 left running throughout and after; CN stayed a healthy 2 on
  both sides of this run (`SHOW CLUSTER` re-checked post-run: both MEMBER).

## Result: group fix PROVEN on the wire; NOT admitted (CN=2)

- **On-wire proof (leg d PASS):** OVMX's MAC (`52:54:00:00:00:f4`) now
  transmits its periodic multicast HELLO to `ab:00:04:01:01:01` (155
  frames over the run) — the lab VAX cluster's own group, confirmed
  byte-identical to VAX2's own multicast HELLO destination in the same
  capture. The E53 wrong-group blocker (`ab:00:04:01:00:00`) is fixed.
- **VAX1 (the coordinator, CSID 00010001) sees it and engages:** 930
  DIRECTED HELLO frames exchanged between OVMX and VAX1 (both VAX1's
  logical LAVC `aa:00:04:00:01:04` and its real HW MAC
  `08:00:2b:1e:85:61`) — sustained, bidirectional, for the full run.
  OVMX's own `SHOW CLUSTER/LOCAL_PORTS` reports `channels 2, circuits 0`,
  `frames tx 755 (errors 0), rx 577 (dropped: nobuf 0, badclass 0)`.
- **VAX2 never engaged OVMX at all** (no frame in this capture has VAX2's
  logical/HW MAC as OVMX's peer) — consistent with VAX1 holding
  `Curr. coord. CSID 00010001` (itself) in its own SDA CLUB block; the
  coordinator does the new-node polling, not every member.
- **The exchange never escalates past HELLO.** Of 3890 SCA frames total,
  2025+42+42=2109 are SCS-ENVELOPE/SCS-SHORT (VAX1<->VAX2's own existing
  session — verified: zero of them name OVMX's MAC as src or dst) and
  1556 are HELLO. OVMX touches exactly 1085 of those HELLO frames
  (155 multicast + 930 directed) and **zero** SCS-ENVELOPE/SCS-SHORT
  frames. No CSB for OVMXJ1 ever appears in VAX1's SDA
  (`ANALYZE/SYSTEM` -> `SHOW CLUSTER` shows only the VAX1/VAX2 CSBs).

## The next gap (not a credential/password gate)

CLUSTER_AUTHORIZE's password field is NOT wired onto the wire yet
(`src/libvms/include/cluster_authorize.h`: "No hashing, no wire use yet
— the password field is stored in the clear for now"), so nothing
carrying a credential was ever sent for a real VAX to accept or reject —
this run cannot be, and is not, a password-rejection. What actually
happens: VAX1 discovers OVMX (group fix worked), polls it with a
sustained directed-HELLO channel-formation exchange, and OVMX's own port
view agrees a channel came up (`channels 2`) — but **virtual-circuit
formation (the step after channel-up that would open the first SCS
connection, e.g. VMS$VAXcluster) never starts on either side**: no VC
class frame appears anywhere in this capture, `circuits 0` the entire
run, and CLUSTER_NODES stays 2 on VAX1 throughout.

This pins the next gap precisely: **channel-up -> virtual-circuit
formation escalation**, not admission/authorization. Needs its own
measure-first investigation (does OVMX's channel FSM have a trigger to
attempt VC formation once a channel is verified? does VAX1 expect a
specific frame class from OVMX to begin VC negotiation that this capture
never shows leaving OVMX?) before the CLUSTER_AUTHORIZE password
question (vms-732) is even reachable.
